# 後端採用 Go

PRD 沒有鎖定後端語言（Q-14），SA 的建議是 Python（FastAPI）。這個產品的核心是每 3 分鐘對最多 50 台交換器做 SNMP 讀取、合計數萬筆 ARP，並且要長時間穩定地跑在每個園區的一台主機上。我們選擇 Go：它的 SNMP、LDAP、RADIUS 與 Excel 程式庫都成熟，並行輪詢是語言的強項，輪詢與 Web 可以放在同一個行程，編譯結果是單一執行檔，容器映像小且容易以非 root 執行。

## 考慮過的做法

- **Python（FastAPI）**：郵件範本與 Excel 的工具最順手，開發速度快。但純 Python 的 SNMP 程式庫解析大量資料時很吃 CPU，輪詢與 Web 同行程時會拖慢網頁回應，多半得把輪詢拆成獨立的行程。
- **TypeScript（Node.js）**：前後端同一種語言。但 SNMP v3 與 RADIUS 的程式庫選擇少，產品最核心的輪詢落在最弱的環節。

## 後果

- 排程器、API 與前端靜態檔都在同一個 `app` 容器裡，不需要訊息佇列或獨立的工作行程。
- 一般的 Web API 與資料存取要寫的程式碼比 Python 多。
- 如果日後負責維護的人只熟 Python，這個決定要重新評估；屆時輪詢應從一開始就拆成獨立行程。
