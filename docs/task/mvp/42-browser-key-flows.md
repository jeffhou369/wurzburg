# 42 — 瀏覽器關鍵流程

Status: resolved
Blocked by: 41

## 要做什麼

由第 33 張拆出（待補驗證第 4 項）。`docs/plan/mvp-spec.md` 的「測試決定」定下：前端不另開接縫，以瀏覽器在同一套環境走少數關鍵流程。目前 Angular 的 ChromeHeadless 測試是元件測試，後端以替身回應，不等於這些流程在真實後端上走通過。`test/browser/review-smoke.js` 只涵蓋郵件連結的登入後導向，而且需要手動啟動環境。

1. **測試環境**
   - 以自動化方式啟動一套隔離的環境：真實的 Go 後端（內嵌建置後的前端）、MariaDB，以及第 41 張的模擬外部系統。不得使用既有部署的容器名稱與 volume（`wurzburg-db-data`）。
   - 不攔截網路、不偽造 API 回應、不使用測試身分標頭。
2. **要走通的流程**（以 Playwright 執行）
   - 登入：本機系統管理員初次登入、強制改密碼；一般使用者以組織帳號登入；未登入時導向登入頁並在登入後回到原目的地
   - 設定精靈：走完五個步驟
   - 登記：單筆登記與批次登記
   - 批次重新確認
   - 裁決衝突
   - 把網段改為不納管：預覽受影響筆數、確認、IP 紀錄被刪除
3. **檢查重點**
   - 每個流程驗證畫面上的結果，並確認狀態同時有文字表達（不只靠顏色）。
   - 流程中瀏覽器主控台沒有錯誤，沒有失敗的 API 請求（刻意測試的錯誤情境除外）。
4. **CI**
   - 評估執行時間後決定是否納入 `Code Quality gate`；若不納入，改為可手動觸發的工作流程，並在 `## Comments` 記錄原因。
5. **整理**
   - `test/browser/review-smoke.js` 併入新的流程或移除。

## 不在範圍內

- 跨瀏覽器與行動裝置版面。
- 郵件用戶端呈現（第 35 張，需要人來驗證）。
- 視覺回歸比對。

## Comments

- 2026-11-13：由第 33 張拆出。

- 2026-11-13：實作完成。
  - 執行方式：`test/browser/run.sh`。它建置前端、內嵌進後端，再跑 `TestBrowserFlows`。該測試用 Testcontainers 啟動 MariaDB、snmpsim、OpenLDAP、Mailpit，以後端內嵌的前端在本機隨機埠提供服務，然後執行 Playwright。只有設定 `WURZBURG_BROWSER_TESTS=1` 才會跑，所以一般的 `go test` 不會啟動瀏覽器。
  - 流程（`test/browser/flows/key-flows.spec.ts`，本機一次通過，約 18 秒）：
    1. 未登入開啟 `/subnets` 會導到登入頁並保留 `returnUrl`；密碼錯誤留在登入頁；初始帳密登入後強制改密碼，目的地保留。
    2. 設定精靈五個步驟：公開網址、AD 測試登入、寄測試信、SNMP 測試讀取、納管兩個發現的網段。完成後回到原本的網段頁。
    3. 工作臺以文字標示未登記。
    4. 登出後以組織帳號登入，側欄顯示名稱與「一般使用者」。
    5. 單筆登記與批次登記。
    6. 批次重新確認。
    7. 已登記位址換 MAC 後，系統管理員裁決為採信新 MAC 並保留登記。
    8. 把網段改為不納管：先看到會刪除的筆數，確認後 IP 紀錄從工作臺消失。
  - 流程中的主控台錯誤與失敗的 API 請求會讓測試失敗。刻意的 401（未登入、密碼錯誤）有宣告為預期。
  - 過程中修了兩個畫面問題：交換器頁按「立即同步」後「同步中」不會自己消掉，改為等這一輪結束再更新；設定精靈的測試按鈕改為先儲存再測試，並補上公開網址與 TLS 選項，否則全新安裝無法在精靈裡走完。側欄補上登出。
  - 觸發同步的 API 在回應前就標記進行中，否則緊接著查狀態會以為這一輪已經結束。
  - CI 納入 `Code Quality gate`（Browser Flows）。本機這套約 18 秒，加上建置前端與啟動容器，CI 逾時設 25 分鐘。
  - `test/browser/review-smoke.js` 已移除，由這套流程取代。
