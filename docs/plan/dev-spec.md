## 1. 範圍與部署前提

Würzburg 是內部用的 IPv4 管理系統。它定時讀取交換器的 ARP table，為納管網段內的每個位址維護一筆 IP 紀錄，讓使用者登記自己負責的位址，並以郵件通知未登記的位址與即將到期的登記。

部署單位是園區：一個園區裝一套，各有自己的 Compose 與資料庫。不做多租戶，也不做跨園區的統一管理（ADR 0009）。

安裝文件必須列出下列部署前提條件：

1. 各網段的 L3 閘道在 Cisco 交換器上，平台為 IOS-XE 或 NX-OS。閘道在防火牆或路由器上的網段，系統看不到。
2. 園區內的 IPv4 位址不重疊，包含不同 VRF 之間。
3. 交換器已開啟唯讀的 SNMP（v2c 或 v3）；有 VRF 時，交換器端已替每個 VRF 設好對應的 context。

設計目標的規模：

| 項目 | 上限 |
| --- | --- |
| ARP 來源交換器 | 50 台 |
| 網段 | 100 個 /24 |
| IP 紀錄 | 約 25,000 筆 |
| VRF 讀取設定 | 合計 200 筆 |

凡是因園區而異的值（顯示名稱、時區、各種天數與次數）一律做成設定並附預設值，見第 10 節。

## 3. 領域模型

### 3.1 交換器與 VRF 讀取設定

- 系統裡的交換器都是 ARP 來源交換器。可填的資料：名稱、管理 IP、平台（IOS-XE 或 NX-OS）、SNMP 版本、埠、逾時、備註、是否啟用，以及一個純顯示用的標籤（例如「核心」）。
- 每台交換器有一到多筆 VRF 讀取設定。每筆包含 VRF 的顯示名稱，以及讀取它所需的資料：v3 是 context 名稱，v2c 是該 VRF 專屬的 community。全域 VRF 那一筆固定存在，不能刪除。
- VRF 清單由系統管理員手動輸入，系統不自動探索。
- SNMP 憑證儲存後不在介面回顯。
- 停用或刪除一筆 VRF 讀取設定（或整台交換器）時，它名下的 ARP 觀測立即移除。只由它看得到的 IP 紀錄因此變為離線，後續照第 3.4、3.7 節處理。

### 3.2 網段、排除範圍與閘道位址

**來源。** 每一輪輪詢除了 ARP 表，也讀同一個 VRF 的介面位址表。每個 L3 介面上設定的位址與遮罩構成一個網段。系統管理員也可以手動新增網段。系統不從主機位址推測遮罩（ADR 0011）。

**狀態。** 每個網段只有一個狀態：

| 狀態 | 意義 | 位址是否有 IP 紀錄 |
| --- | --- | --- |
| 待檢視 | 剛被發現，系統管理員尚未決定 | 否 |
| 納管 | 系統管理員決定要管 | 是（扣除排除範圍與閘道位址） |
| 不納管 | 系統管理員決定不管，必須選原因（DHCP、無線、其他），可加說明 | 否 |

- 新發現的網段一律是待檢視。側欄的「網段」顯示待檢視的數量。
- 待檢視只是初始狀態；系統管理員做過決定後，只能在納管與不納管之間切換。
- 多台交換器回報同一個 CIDR 時是同一個網段。
- 網段互相包含時（例如手動新增的 /16 與發現的 /24），位址歸屬最長的前綴。
- 交換器上已經不存在的網段不自動刪除，改在網段清單標示「來源已消失」，由系統管理員決定。

**排除範圍。** 納管的網段底下可以設定一到多段連續位址，各附原因（DHCP、無線、其他）。範圍內的位址視同不納管。

**閘道位址。** 出現在介面位址表裡的位址是閘道位址，不建立 IP 紀錄，改在網段的詳細資料中顯示。HSRP／VRRP 的虛擬位址不在介面位址表裡，照一般位址處理，由系統管理員登記。

**未定前綴。** ARP 觀測的 IP 不落在任何已知網段時，列入未定前綴清單（IP、MAC、交換器、VRF、介面），不建立 IP 紀錄。系統管理員可以為它們手動新增網段。

### 3.3 IP 紀錄：身分、建立與刪除

- 一個 IPv4 位址在系統內只有一筆 IP 紀錄，不因 VRF 而區分。
- 建立條件：ARP 觀測的 IP 落在納管的網段、不在排除範圍內、不是閘道位址，且 ARP 類型不是 invalid。靜態與動態的 ARP 都建立，類型保留供顯示與篩選。
- 刪除條件：網段改為不納管，或位址被劃入排除範圍。此時 IP 紀錄直接刪除，連同它的衝突與通知去重狀態（ADR 0013）。
- 修改網段的 CIDR 或刪除手動新增的網段，導致位址不再屬於任何納管網段時，適用同一條刪除規則。
- 刪除前的防護：
  - 儲存前顯示確認對話框，寫明將刪除幾筆 IP 紀錄、其中幾筆有擁有者，系統管理員再次確認才執行。
  - 稽核紀錄記下操作者、時間、網段或範圍、刪除筆數；有擁有者的 IP 紀錄逐筆記下 IP、MAC、擁有者、擁有者信箱與到期日。
- 重新納管後，那些位址以全新的未登記 IP 紀錄出現，並在下一次未登記彙整中列為新增。

### 3.4 在線狀態

- 系統為每一組「IP 紀錄 × VRF 讀取設定」保存一筆目前的 ARP 觀測：MAC、介面、ARP 類型、最後見到時間。
- 某筆 VRF 讀取設定成功讀取、卻沒有回報某個原本看得到的 IP 時，該筆觀測的「未見輪數」加一；達到離線判定輪數（預設 2）時移除該筆觀測。讀取失敗的輪次不計。
- IP 紀錄只要還有任何一筆觀測就是在線；全部移除後是離線。任一來源重新看到就立刻恢復在線。
- 介面與文件必須如實說明：在線代表交換器的 ARP table 裡仍有這個位址，裝置實際離開後要等交換器的 ARP 逾時才會變成離線。安裝文件建議網管視需要調短 ARP 逾時。
- 系統只保存目前的狀態與變更事件（首次見到、MAC 變更、在線與離線的切換），不保存每一輪的完整觀測。

### 3.5 登記與擁有者

**登記狀態。**

| 狀態 | 意義 |
| --- | --- |
| 未登記 | 沒有擁有者 |
| 已登記 | 有擁有者，且在有效期內 |
| 已到期 | 有擁有者，但超過有效期而未重新確認 |

「即將到期」是由到期日推算的篩選條件與標示（到期前 14 天內），不是儲存的狀態。在線狀態、登記狀態與衝突三者互相獨立，介面、郵件與匯出都要能表達「在線 · 未登記」這類組合。

**擁有者。** 擁有者是完成登記的帳號，能不能編輯一筆登記只看帳號（ADR 0012）。擁有者信箱是到期催認的收件地址：使用 AD 時自動帶入目錄裡的信箱並可修改，使用 RADIUS 時由使用者自己填。它可以是共用信箱，不決定任何權限。

**登記欄位。** 擁有者信箱（必填，格式校驗）、裝置類型（自由文字，不從 OUI 推斷）、主機名稱（選填）、備註（選填）。備註欄旁註明「所有登入者都看得到」。

**動作與權限。**

| 動作 | 一般使用者 | 系統管理員 |
| --- | --- | --- |
| 檢視所有 IP 紀錄的所有欄位 | 可以 | 可以 |
| 登記未登記的 IP 紀錄 | 可以，自己成為擁有者 | 可以 擁有者可指定為自己或任一已存在的帳號 |
| 編輯登記、重新確認、釋放 | 僅限自己是擁有者的 | 任何一筆 |
| 改派給另一個帳號 | 不可以 | 可以 對象限已存在的帳號 |
| 匯出 Excel | 可以，內容與畫面一致 | 可以 |

- 登記不需要核准，立即生效，並寫入稽核紀錄。
- 重新確認把到期日設為當天加上有效期（預設 365 天）。
- 釋放使 IP 紀錄回到未登記。
- 所有權限在 API 逐筆判斷；寫入不屬於自己的登記回 403。

**批次操作。** 表格支援多選，也能一次勾選目前篩選結果的全部。可批次登記（同一組欄位值套用到所有勾選的未登記 IP 紀錄）、批次重新確認、批次釋放；批次改派僅限系統管理員。權限逐筆檢查，沒有權限的略過，並在結果中列出哪些沒有成功與原因。

### 3.6 衝突

**何時開衝突。** 每一輪把某個 IP 目前所有 ARP 觀測的 MAC 整理成一個集合，與採信 MAC 比較：

| 情況 | 條件 | 處理 |
| --- | --- | --- |
| 並存 | 集合中有兩個以上不同的 MAC | 開衝突 |
| 有擁有者的 IP 換了 MAC | IP 紀錄有擁有者；集合只有一個 MAC，且與採信 MAC 不同 | 開衝突，登記不變 |
| 未登記的 IP 換了 MAC | IP 紀錄沒有擁有者；集合只有一個 MAC，且與採信 MAC 不同 | 不開衝突；採信 MAC 改為新的，記下 MAC 變更事件 |

多台交換器回報同一個 IP、同一個 MAC 是正常情況，不算衝突。一筆 IP 紀錄同時最多只有一筆尚未解消的衝突。

**狀態。** 未處理、處理中、已解消。

**裁決（僅系統管理員，MVP 為單筆處理）。** 衝突的詳細資料顯示每個 MAC、各自出現在哪台交換器與哪個 VRF、首次與最近見到的時間。系統管理員選擇其一並可加註：

| 裁決 | 結果 |
| --- | --- |
| 採信新的 MAC，登記保留 | 採信 MAC 更新，衝突已解消 |
| 採信新的 MAC，登記釋放 | 採信 MAC 更新，IP 紀錄回到未登記，衝突已解消 |
| 維持原本的 MAC | 衝突進入處理中 |

處理中的規則：

- 採信 MAC 與登記都不變。
- 另一個 MAC 繼續被看到時不重複開衝突，也不計入「未處理」的數字。
- 另一個 MAC 連續達到離線判定輪數不再出現後，衝突自動已解消。
- 系統管理員可以重新打開處理中的衝突，改選另外兩種裁決。

未處理的衝突，若 MAC 不一致自行消失（集合恢復成只有採信 MAC），自動已解消並註記為自行消失。

批次處理與套用前預覽留到 Beta。新衝突除了 Toast，側欄要有未處理的計數。

### 3.7 自動清除

同時符合「未登記」與「離線」的 IP 紀錄，離線超過清除天數（預設 90 天，0 代表停用）後自動刪除，稽核紀錄記下筆數。有擁有者的 IP 紀錄不論離線多久都不會被自動清除。被清除的位址日後再出現，就是一筆全新的未登記 IP 紀錄。

## 4. 採集

- 每 3 分鐘一輪。每筆啟用中的 VRF 讀取設定在一輪中讀三樣資料：ARP 表（MIB-II `ipNetToMediaTable`，OID `1.3.6.1.2.1.4.22`）、介面位址表、介面名稱。後兩者實際採用的 MIB 物件在蒐集回應範例時確定。
- 只處理 IPv4。ARP 類型為 invalid 的列忽略。
- 單筆 VRF 讀取設定讀取失敗時立即重試一次，仍失敗就略過到下一輪。總嘗試次數固定為 2，SNMP 程式庫本身的重試要關閉，避免疊加。
- 一筆失敗不影響其他 VRF 讀取設定，包含同一台交換器上的其他 VRF。失敗的那一輪，它名下的 ARP 觀測維持不變。
- 並行：不同交換器之間有上限地並行（預設 12）；同一台交換器上一次只讀一筆 VRF 讀取設定。
- 上一輪還沒結束時，下一輪不重疊啟動，並在介面顯示「本輪未完成」。
- 每一輪的結果以批次寫入資料庫。
- 每筆 VRF 讀取設定記錄每次讀取的開始與結束時間、成功或失敗、是否重試、筆數與錯誤類別（逾時、認證失敗、連線被拒、無資料）。
- 系統管理員可手動觸發「立即同步」。
- 介面顯示 ARP 觀測的介面名稱（例如 `Vlan10`），不另外做 VLAN 欄位。

**採集模組的邊界。** 採集模組對系統其他部分只輸出三樣東西：ARP 觀測、介面位址、介面名稱。平台差異全部封在模組內部，實機回應與範例不同時，只需要修改這個模組。模組附一個命令列入口，可對指定的交換器執行讀取並把原始回應存成測試資料檔。

**測試資料。** 開發前先蒐集 IOS-XE 與 NX-OS 的回應範例（原廠文件、MIB 定義、公開的實際輸出），存成測試資料檔放進倉庫，每一份註明來源網址與平台版本。自動化測試的 SNMP 模擬器回放這些檔案。實機驗證見第 12 節。

## 5. 驗證與權限

**兩條分開的登入路徑。** 登入頁有「組織帳號」與「系統管理員」兩個入口，不依帳號自動判斷後端。

**一般使用者。**

- 一個園區只啟用一種驗證來源：AD（LDAPS）或 RADIUS（PAP）。兩種都在 MVP 完成。
- 帳號在第一次登入成功時自動建立。
- AD 可設定只允許某個群組的成員登入，留空代表所有 AD 帳號都能登入；登入時取得信箱與顯示名稱。
- RADIUS 驗證通過即可登入；顯示名稱就是帳號，沒有信箱。
- 上線後更改驗證來源時，設定頁要警告：原有的擁有者帳號將無法登入，名下的登記需要系統管理員改派。

**系統管理員。**

- 系統內建的本機帳號，不經過驗證來源。
- 密碼以 Argon2id 雜湊；至少 12 個字元；連續失敗 5 次鎖定 15 分鐘。
- 可以有多個，由現有的系統管理員建立與停用；系統至少保留一個啟用中的。
- 忘記密碼時在主機上執行管理指令重設，不提供網頁上的忘記密碼功能。

**工作階段與傳輸。**

- 工作階段存在伺服端，可撤銷；閒置 8 小時逾時。Cookie 設 HttpOnly 與 SameSite，在 HTTPS 後面時加 Secure。
- 變更類的請求防 CSRF；登入有速率限制。
- 預設安裝是 HTTP。倉庫另附選用的 Nginx 與憑證的 Compose 範例。
- 不在 HTTPS 後面時，登入頁顯示明文傳輸警告。

**Secret。** SNMP 憑證、AD 查詢帳號密碼、RADIUS secret、SMTP 密碼加密後存在資料庫，金鑰由環境變數或掛載檔提供；金鑰遺失就要重新輸入這些 secret。所有 secret 儲存後不回顯，不出現在日誌、稽核紀錄、錯誤頁、URL 與郵件本文。

## 6. 通知

通知只走 SMTP。MVP 有三種信，每種都是 `multipart/alternative`，HTML 與純文字的資訊對等，版面與相容性照 PRD 第 11 節。

| 信件 | 收件人 | 時機 | 內容 |
| --- | --- | --- | --- |
| 未登記彙整 | 系統管理員收件清單 | 每小時整點 | 這段時間新出現的在線且未登記的 IP 紀錄；沒有新增就不寄 |
| 未登記總表 | 系統管理員收件清單 | 每週一次，預設週一 09:00 | 所有已通知過、至今仍在線且未登記的 IP 紀錄；沒有項目就不寄 |
| 到期催認 | 擁有者信箱 | 見下 | 即將到期或已到期的登記 |

**未登記的去重。**

- 去重鍵是 `unreg|{ip}|{採信 MAC}`。
- 成功寄出後才標為已通知。SMTP 失敗時以有限次數重試，失敗的不得標為已通知，並在管理介面可見。
- 已通知的狀態在下列情況解除：完成登記、IP 紀錄被刪除、系統管理員手動重設。裝置離線不解除。
- 未登記的 IP 換了 MAC 會產生新的去重鍵，因此會再被列為新增一次。
- 未登記彙整的明細最多列 50 筆，超過時註明其餘請到系統檢視。未登記總表的版面沿用未登記彙整。

**到期催認的時程。**

1. 到期前 14 天寄一次。
2. 到期當天寄一次。
3. 之後每 7 天復催一次，最多 4 次。
4. 催完仍未回應就停止寄信；IP 紀錄維持已到期，擁有者與備註保留，不自動釋放。

- 只有最後一次復催副本給系統管理員收件清單。
- 同一個擁有者信箱同一天有多筆要催，合併成一封，連結指向已篩選的清單。
- 去重鍵包含 IP、到期日與催認輪次；重新確認後到期日改變，催認重新開始。

**共通規則。**

- 信中的連結只通往需要登入的頁面，郵件裡不放可直接寫入的權杖。
- 使用者輸入的文字進入郵件 HTML 前要跳脫。
- 每一封的寄送結果寫入通知紀錄。
- SMTP 或驗證來源中斷不得影響採集與 Web 介面。

## 7. 首次啟動與設定精靈

**第一個系統管理員。**

- 在 Compose 的環境變數提供帳號與初始密碼（建議名稱 `WURZBURG_ADMIN_USERNAME`、`WURZBURG_ADMIN_PASSWORD`）。系統啟動時若還沒有任何系統管理員，就用它建立帳號。
- 第一次登入強制修改密碼，新密碼要符合密碼政策，改完才進入設定精靈。
- 已經有系統管理員之後，這兩個環境變數不再有任何作用。
- 初始密碼不寫進任何日誌。安裝文件提醒在首次登入後把它從設定檔移除。

**設定精靈。** 系統管理員第一次登入並改完密碼後自動開啟，依序五步：

| 步驟 | 內容 | 測試 |
| --- | --- | --- |
| 1 園區資訊 | 顯示名稱、時區 | — |
| 2 驗證來源 | 選 AD 或 RADIUS，填連線資料 | 以一組帳密測試登入 |
| 3 郵件 | SMTP、系統管理員收件清單 | 寄測試信 |
| 4 第一台交換器 | 管理 IP、SNMP 版本與憑證、VRF 讀取設定 | 測試讀取 |
| 5 檢視網段 | 把發現的網段設為納管或不納管 | — |

- 每一步都可以按「稍後再設定」跳過。
- 精靈結束後，首頁顯示「尚未完成的設定」清單，列出跳過的項目與各自的後果，並包含「尚未啟用 HTTPS」；全部完成後清單消失。
- 精靈可以從設定頁重新開啟。

## 8. 前端

- 框架是 Angular（ADR 0014）。版本與 Lucide 在 Angular 上的用法在開始前端工作時查最新文件後確定。
- 元件自己寫，行為的部分（浮層、對話框的焦點管理、鍵盤操作、無障礙屬性、表格）用 Angular CDK。不使用 Angular Material 或其他元件庫的外觀。
- 樣式以 `docs/Wurzburg-UI-Style-Kit.zip` 的原始檔為準，其次是樣式包內的 `CLIProxyAPI-UI-style-reference.md`，最後是 PRD 第 10 節。設計 token 以 CSS 變數集中管理。
- 設計過程使用 UI UX Pro Max：以「內部營運／IP 管理儀表板」產生設計系統並執行交付前檢查，產出存成 `design-system/ip-mgmt/MASTER.md`；它產生的色盤不得覆蓋樣式包的色票。這個 skill 目前沒有安裝，開始前端工作前要先裝好。
- MVP 完成淺色主題（EasyCLIProxyAPI `light`），並保留主題切換的機制。
- 介面語言是繁體中文；文字集中管理，不散落在元件裡。
- 版型、各畫面的結構、燈號與灰階規則、無障礙檢查清單照 PRD 第 10 節。
- 表格一律由伺服端分頁、排序與篩選。
- 前端建置後的靜態檔包進後端的執行檔；前端的 API 型別由 OpenAPI 描述檔產生。

## 11. MVP 範圍

**MVP 包含：**

- 採集：v2c 與 v3、VRF 讀取設定、IOS-XE 與 NX-OS、介面位址表與介面名稱、重試與失敗隔離、立即同步。
- 網段：發現、三種狀態、排除範圍、閘道位址、未定前綴、手動新增與修正。
- IP 紀錄：建立與刪除規則、在線與離線、自動清除。
- 登記：單筆與批次的登記、編輯、重新確認、釋放、改派。
- 衝突：偵測與單筆裁決。
- 首頁工作臺：儀表板、IP 表格（搜尋、篩選、分頁、多選）、Excel 匯出。
- 驗證：AD、RADIUS、系統管理員本機帳號、工作階段。
- 通知：未登記彙整、未登記總表、到期催認，各含 HTML 與純文字，並在 Outlook、Gmail、Apple Mail 測試。
- 首次啟動與設定精靈、未完成清單。
- 本地 OUI（照 PRD ADR-004）、稽核紀錄、健康檢查。
- Docker Compose 部署、選用的 HTTPS 範例、安裝文件。
- 淺色主題。

**留到 Beta：** 衝突的批次處理與套用前預覽、檔案匯入登記、儀表板數字連動篩選（FR-38）、稽核紀錄的篩選與匯出（FR-62）、深色或暖沙主題、唯讀稽核角色（Q-16）。

**之後另議：** 「MAC 接在哪個埠」、以網段為單位的檢視權限、多語系介面、同一園區並存兩種驗證來源。

## 12. 實機驗證清單

不做獨立的 PoC 階段。在下列項目經實機確認之前，採集行為是依據文件與公開範例，文件中要如此註明。設備到位時，用採集模組的命令列入口在 IOS-XE 與 NX-OS 上各執行一次，逐項確認並把真實回應存成新的測試資料檔。

| 要確認的事 | 影響 |
| --- | --- |
| 兩個平台的 ARP 表各自回傳什麼 | 採集的基礎 |
| v2c 用各 VRF 專屬的 community、v3 用 context 名稱，是否都讀得到各 VRF 的 ARP | 3.1 |
| 介面位址表是否完整，secondary 位址是否包含在內 | 3.2 |
| 交換器自己的介面位址與 HSRP／VRRP 虛擬位址在 ARP 表裡如何呈現 | 3.2 |
| 兩個平台的 ARP 逾時預設值 | 3.4 的說明文字 |
| 介面名稱是否讀得到、與 ARP 的介面索引是否對得上 | 4 |
| 讀取數千筆 ARP 實際需要多久 | 並行數與逾時 |

VRF 相關的公開範例最難取得，因此 VRF 讀取設定是最可能在實機驗證時需要調整的部分。
